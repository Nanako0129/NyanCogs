# 把 Jev 導入 MessageWatch

本檔案詳細記錄 MessageWatch 如何整合 [TypeSafe](https://docs.typesafe.ai) 的 Jev（System One 模型），並記載各項門檻與設計選擇背後的實測量測數據。

關於本 cog 的整體架構與 Discord 端實作機制，請參閱 [MessageWatch 架構決策](messagewatch-design.md)。

以下記錄的所有機率與信心度數值，皆**直接以 `jev-1.13.0` 實測取得**。尚未量測的維度皆已明文標示。

---

## 1. 為什麼是 System One，不是生成式模型

MessageWatch 需要校準後的數值機率以進行明確的數值比對，而非非結構化的文字段落。

當生成式模型輸出「這段話看起來像詐騙」這類自然語言時，應用程式必須建立容易出錯的正規表示式解析層，或者將決策權交由未校準的散文。相對地，Jev 輸出包含明確機率的型別化資料：
- `noul`：回傳指定條件是否成立的機率值。
- `choice`：回傳選定的選項與對應的信心度。
- `score`：回傳在離散有序等級間的連續加權分數。

所有的決策邏輯──門檻比對、否決判斷與多條件組合──皆完全保留在 Python 程式碼中。調整判定門檻既不需要重跑推論，亦不需要修改 prompt 措辭。

模型名稱在程式原始碼中固定宣告為 `MODEL = "jev-1.13.0"`，避免使用如 `jev-latest` 這類浮動別名。由於門檻數值是針對特定模型權重量測校準的，若模型版本隨供應商更新而變動，將導致既有門檻默默失去校準意義。

## 2. 一次請求長什麼樣

每一次的推論請求酬載皆結構化為三個明確欄位：

```text
state        = 匿名化後的訊息陣列（文字、順序索引、u1/u2 代稱、頻道名稱）
instructions = 該提問的分類目標指示
criteria     = 區分各項可能結果的具體語意定義
```

Discord 使用者 ID、伺服器暱稱與頭像雜湊絕不對外發送。作者身分在請求前動態替換為暫時性的標籤（`u1`、`u2`），每次請求重新產生且不儲存。同一個使用者在不同請求間會獲得不同的代稱，避免跨視窗追蹤資訊流出機器人本體。

一個標準的評估視窗（包含 8 條頻道規則與 5 則訊息）約消耗 1,500 個 input tokens。以每百萬 input tokens 0.042 美元計（`DEFAULT_TOKEN_PRICE_PER_MILLION = 0.042`），單次請求花費約為 0.00006 美元，output tokens 則免計費。

## 3. 每一種判斷對應一種 primitive

| 判斷任務 | Primitive | 運作考量 |
|---|---|---|
| 詐騙偵測（`any_scam`） | `noul` | 評估二元條件是否成立；回傳校準後的機率 |
| 敵意偵測（`is_hostile`） | `noul` | 獨立二元評估；詐騙與敵意可能同時存在，故分成兩道獨立查詢 |
| 人際衝突程度（`heat`） | `score` | 跨連續有序等級（0 至 3）的程度評分，而非二元是非判斷 |
| 違規條文辨識（`which_rule`） | `choice` | 從既定的候選規則中選取條文；需要信心度數值 |
| 違規訊息辨識（`scam_index`, `rule_index`） | `choice` | 指出視窗中具體違規的訊息索引 |
| 版規討論辨識（`is_meta` / `meta_index`） | `noul` / `choice` | 避免誤判的否決過濾機制；詳見第 6 節 |

針對同一組 `state` 的多道獨立提問會打包於單次批次請求中。各題目平行運算，彼此無法窺探對方的判定結果，最後由 Python 程式碼決定如何消費與過濾。

## 4. 版規放 criteria，不放 state

將頻道版規定義在 `criteria` 而非 `state`，避免了 TypeSafe 官方說明指出的兩項失效模式：

- **Jaggedness #5（過多無關 state 降低準確度）**：當 `state` 包含大量無關資訊時，推論準確度會顯著下降。對於單一 8 則訊息的視窗而言，伺服器的大多數版規皆與當前對話無關。
- **Jaggedness #6（state 視為未驗證資料）**：模型將 `state` 視為未經審查的 raw data，不具備指示權威。若將規則放置於 `state` 中，成員可在聊天中試圖改寫或偽造規則。放在 `criteria` 則無法被成員發言竄改。

實測驗證：
- **通用 8 條版規對照 4 組測試案例（廣告、人身攻擊、洩漏個資、正常對話）**：條文與違規訊息辨識皆達 4/4 準確。違規案例機率為 0.92–0.97；正常對話機率為 0.04。
- **樹洞自訂版規對照 9 組典型案例**：判定準確度達 9/9。違規案例機率為 0.94–0.98；合規回應機率為 0.05–0.08。

## 5. 選項標籤必須是規則原文

在早期試驗中，`choice` 的選項是以序數命名（「規則 1」、「規則 2」等）。模型在連續 6 次執行中皆發生分類錯誤。

此項失敗歸因於 TypeSafe jaggedness #4（間接指涉失效）：序數標籤本身不具備語意，迫使模型必須在外部條文間進行額外的索引轉換，該步驟極易出錯。將選項標籤替換為規則原文後，同一組測試集的判定錯誤立即歸零。

PR #29 在詐騙偵測中亦遇到相同狀況：以序數指向視窗中第幾則訊息（例如「第 6 則訊息」）時，在信心度 0.77 至 0.93 的高分區間仍反覆指錯。改為 echo 各候選訊息開頭的前幾個字元（`SCAM_OPTION_LABEL_CHARS = 48`）後，所有測試案例皆以 0.98 至 1.00 的信心度正確鎖定。

原則：在 choice 選項中標示目標時，標籤應採用原文內容，絕不使用編號索引。

## 6. `meta_index`：一道否決題

在張貼了版規的頻道中，成員之間經常互相提醒規範。例如發言「你這樣算下指導棋喔」是在指出他人違規，而非違規本身。在基準測試中，模型將該提醒評為 0.84 的機率違反第 2 條。

在 `criteria` 與 `instructions` 中補充排除指示（「指出他人違規不構成違規」）無法解決此問題。這屬於 jaggedness #1（字面關鍵字匹配）：句中出現了「下指導棋」字串，直接觸發了文字模式匹配。

有效的解決架構是將版規討論拆為獨立的提問，再由程式碼否決。

這道題目存在兩種形狀，而本文件早期版本只描述了第一種。實測是對一道名為 `is_meta` 的 `noul` 做的，問的是「這則訊息是不是在討論頻道版規」：

- 版規討論案例：0.56、0.92、0.92。
- 真實違規發言：0.06、0.08。
- 重新驗證關鍵 5 組邊界案例：5/5。

實際出貨的是一道名為 `meta_index` 的 `choice`，問的是「**哪一則**訊息在討論版規」，並以 `"沒有任何一則在談論這個頻道的規則"` 作為無匹配選項。否決只在該 index 等於 `rule_index` 指出的那一則時才觸發，所以有人指出別人違規，不會再連帶壓掉同一個視窗裡另一則真正的違規——整窗否決的 `noul` 會。

因此上面那組數字量的是早期的形狀。逐訊息的版本尚未對那 19 個案例重新量過。

提示詞措辭極度敏感：

| `is_meta` 提示詞措辭版本 | 基準測試準確度（19 案例） | 失效狀況 |
|---|---|---|
| 實測版本在重構時被順手泛化 | 18/19 | 1 個判定錯誤 |
| 定義過寬的措辭 | 17/19 | 錯誤否決了 2 個真實違規 |
| 收斂措辭（「談論這個頻道的規則」） | 19/19 | 0 錯誤 |

一般化一個量測校準過的問題，會使其退化回未校準狀態。

## 7. 機率不夠，還要信心下限

在邊界案例測試中，一則同理回應（「我也是」）在違反版規項給出 0.61 的機率，但對應的 `which_rule` 選項信心度僅有 0.43。模型如實反映了其分類不確定性。

為避免發出條文不確定的通報，版規判定強制執行雙重檢核：
1. `any_violation` 機率 $\ge$ `rule_threshold`（預設為 0.85）。
2. `which_rule` 信心度 $\ge$ `rule_confidence`（預設為 0.70）。

當機率符合 `rule_threshold` 但條文信心度未達 `rule_confidence` 時，系統不會直接抑制該報告，而是在報告中明確指出存在違規但條文不確定（「疑似違規，條文不確定」）。

此信心下限機制不能直接套用於詐騙偵測。在 PR #29 中，詐騙訊息指涉錯誤發生在 0.77 至 0.93 的高信心區間，那是序數標籤間接對應造成的缺陷。信心下限解決的是語意模糊度，無法修正結構性的標籤錯誤。

## 8. 門檻是逐頻道的，因為量出來就是這樣

在不同頻道語境下的實測數據分離情況：

| 頻道語境 | 違規測試案例機率 | 合規測試案例機率 |
|---|---|---|
| 樹洞頻道（具體自訂版規） | 0.94–0.98 | 0.05–0.08 |
| 一般討論頻道（伺服器通則第 8 條） | 0.49–0.96 | 0.04–0.05 |

樹洞頻道的數值分離極為乾淨，在預設 0.85 門檻下運作擁有充裕餘裕。然而伺服器通則第 8 條的違規案例機率最低僅達 0.49，若套用全域 0.85 門檻將會漏判大量真實違規。

此落差源於規則撰寫的具體程度，而非模型能力劣化。樹洞規則逐一列舉具體的禁止行為，而第 8 條則屬於高度抽象的原則性規範。因此系統透過 `[p]watch rule threshold` 支援逐頻道獨立設定門檻。

此外，準則文字的編寫品質會直接影響判定準確度。以維護者口頭說明的標準重新撰寫第 8 條 criteria 後，同一真實案例的機率評分由 0.17 提升至 0.94，且未影響正常對照發言。準則文字的具體度對偵測準確度的影響，高於單純調整數值門檻。

## 9. 兩個量過之後放心的地方

- **篩選後的上下文優於完整上下文傾倒**：直接餵入 25 則原始對話訊息時，目標偵測機率僅為 0.25；若先以預查題目挑出相關訊息後再行判定，偵測機率提高至 0.59 且消耗更少 tokens（符合 jaggedness #5）。
- **前提偵測器不會捏造前提**：為驗證詢問是否存在前提是否會引發模型幻覺，測試了 3 組負向案例（包含 2 組刻意誘導的提示）。量測分數皆落於 0.03 至 0.04，證實該偵測器不會無中生有捏造前提。

## 10. 目前的預設值

| 設定項目識別碼 | 預設數值 | 來源依據 |
|---|---|---|
| `scam_threshold` | 0.90 | 實測量測數值 |
| `hostile_threshold` | 0.80 | 實測量測數值 |
| `heat_threshold` | 2.50 | 實測量測數值（滿分 3；真實伺服器背景最高紀錄為 1.53） |
| `rule_threshold` | 0.85 | 依據第 8 節實測分離數值 |
| `rule_confidence` | 0.70 | 依據第 7 節實測分離數值 |
| `window_size` | 8 | 視窗滑動機制架構設定 |
| `idle_seconds` | 600 | 閒置掃描間隔判定設定 |

## 11. 沒量到的

**召回率。** 本紀錄記載的所有數據皆評估精確率：即在給定已知測試案例下，模型判定的正確比率。計算召回率必須取得線上運作中未被系統通報的真實違規案例，然而合成測試集與管理員標記按鈕皆無法捕捉未通報事件。報告按鈕累積的僅為精確率反饋。

這項限制屬於合成測試架構的方法論邊界，而非暫時性的代辦工作事項。
