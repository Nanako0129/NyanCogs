# 把 Jev 導入 MessageWatch

這份文件記錄 MessageWatch 怎麼使用 [TypeSafe](https://docs.typesafe.ai) 的 Jev
（System One 模型），以及每個決定背後實際跑出來的數字。

cog 本身的架構決策另見 [MessageWatch 架構決策](messagewatch-design.md)。

所有百分比與機率都是**實跑 `jev-1.13.0` 量到的**，不是推估。沒量過的地方會明說沒
量過。

---

## 1. 為什麼是 System One，不是生成式模型

這個 cog 要的不是一段文字，是一個可以拿去比大小的數字。

生成式模型回「我覺得這則有點像詐騙」，程式要拿它做什麼？要嘛再寫一層解析，要嘛就
是把判斷權交給一段沒有校準的散文。Jev 回的是 typed answer 加機率：`noul` 回「是的
機率」，`choice` 回選中的選項加信心，`score` 回有序等級上的加權位置。門檻、否決、
組合邏輯全部留在 Python 裡，流程由程式碼掌控。

因此，調整一個門檻不需要重跑推論，也不需要動 prompt。

模型名稱在程式裡是寫死的 `jev-1.13.0`，不是 `jev-latest`。所有門檻都是對這個版本量
出來的，讓版本自己飄走等於讓門檻悄悄失去意義。

## 2. 一次請求長什麼樣

```
state        = 匿名化後的訊息陣列（text、位置、u1/u2 標籤、頻道名稱）
instructions = 這一題在判斷什麼
criteria     = 這一題的可能答案怎麼區分
```

Discord user ID、顯示名稱、頭像從來不送。作者在送出前被換成 `u1`、`u2` 這種標
籤，每次請求重新產生，不儲存。所以同一個人在兩次請求裡不是同一個 `u1`──這是刻意
的，關聯本來就不該離開這個 bot。

一個視窗（8 條規則 + 5 則訊息）大約 1,500 input tokens。以 $0.042/Mtok 計算約
$0.00006 一次，output 免費。

## 3. 每一種判斷對應一種 primitive

| 判斷 | primitive | 為什麼 |
|---|---|---|
| 這段對話有詐騙嗎 | `noul` | 條件成不成立，回「是的機率」 |
| 這段對話有敵意嗎 | `noul` | 同上；兩者可能同時成立，所以分成兩題而不是一題多選 |
| 火藥味多重 | `score` | 有序程度，不是是非題 |
| 違反了哪一條規則 | `choice` | 從定義好的集合裡選一個，而且需要它的 confidence |
| 這是不是在討論規則本身 | `noul` | 否決用，見第 6 節 |

彼此獨立的問題一次請求一起問──它們平行跑、看不到彼此的答案，程式再決定要用哪
幾個。

## 4. 版規放 `criteria`，不放 `state`

這是 TypeSafe 自己列的 jaggedness 逼出來的：

- **#5 大型 state 裡的無關細節會降低準確度。** 版規對任何一個視窗來說，絕大多數條
  文都是無關的。
- **#6 state 是資料，模型預設不把它當成敵意內容。** 成員訊息就是 state；版規如果也
  放在 state，成員就可以在頻道裡打字改寫規則。放 criteria 成員寫不進去。

實測結果（通用版規 8 條 × 4 案例：廣告／人身攻擊／個資／乾淨）：4/4 指對條文與
訊息，違規 0.92–0.97、乾淨 0.04。

樹洞真實版規 × 9 個典型案例：9/9，違規 0.94–0.98、允許 0.05–0.08。

## 5. 選項標籤必須是規則原文

`choice` 的選項標籤一開始寫成「規則 1」「規則 2」這種序數。模型連錯六次。

原因在 jaggedness #4（間接指涉）：序數標籤本身不帶語意，模型要先在別處把序數對回規
則內容，而那一層對應它做不穩。把標籤換成規則原文之後，同一批案例立刻正確。

這條教訓和 PR #29 的詐騙偵測是同源的──那裡也是用序數指向視窗裡的第幾則訊息，也是
連錯，也是改成回 echo 訊息原文之後才對。

指向任何東西的時候，用它的內容當標籤，不要用它的編號。

## 6. `is_meta`：一道否決題

在貼了版規的頻道裡，成員會互相糾正。「你這樣算下指導棋喔」這句話本身是在指出
違規，不是違規──但模型給它 0.84，判成違反第 2 條。

在 criteria 和 instructions 兩個地方都明寫「指出別人違規不算違規」仍然失敗。這
是 jaggedness #1（字面閱讀）：句子裡出現「下指導棋」這個字串就 match 上了形狀。

有效的做法是文件本身建議的：拆成獨立的字面問題，在程式碼裡否決。新增一題
`is_meta`（noul），問「這則訊息是不是在談論這個頻道的規則本身」，過門檻就整段否決。

- meta 案例：0.56 / 0.92 / 0.92
- 真正的違規：0.06 / 0.08

分離很乾淨。加上這題之後重測關鍵 5 例：5/5。

措辭很敏感，而且是往兩個方向壞的：

| `is_meta` 的問法 | 19 個案例的結果 |
|---|---|
| 從實測版本「順手一般化」過的措辭 | 18/19 |
| 過寬的措辭 | 17/19（吞掉兩個真違規） |
| 收斂到「談論這個頻道的規則」 | 19/19 |

一般化一個量過的問題，就是把它變回一個沒量過的問題。

## 7. 機率不夠，還要信心下限

邊界案例「我也是」：違規機率 0.61，但 `choice` 的信心只有 0.43。模型正確地
表達了它不確定。

所以規則判斷的條件是兩個都要過：違規機率 ≥ `rule_threshold`（預設 0.85）且
`which_rule` 的信心 ≥ `rule_confidence`（預設 0.70）。

這條不能套用到詐騙偵測。PR #29 裡詐騙指錯訊息的時候，信心是 0.77–0.93──信心
門檻救不了那個問題，那個問題是第 5 節的標籤問題。兩者的失敗模式不同，修正方式不可互換。

## 8. 門檻是逐頻道的，因為量出來就是這樣

| 頻道 | 違規案例的機率 | 乾淨案例的機率 |
|---|---|---|
| 樹洞（自訂版規） | 0.94–0.98 | 0.05–0.08 |
| 一般頻道（伺服器規則第 8 條） | 0.49–0.96 | 0.04–0.05 |

樹洞的分離非常乾淨，0.85 的門檻綽綽有餘。伺服器規則第 8 條的違規案例卻低到 0.49，
同一個 0.85 會整批漏掉。

這個落差不是模型變差，是規則本身寫得多具體的差別──樹洞的版規把禁止的行為一條
一條寫死，第 8 條是一句概括。所以門檻做成 per-channel（`[p]watch rule threshold`），
而不是找一個「正確的」全域值。

另一半的解法是把規則寫清楚。用維護者自己口頭解釋第 8 條的內容重寫 criteria 之後，
同一個真實案例從 0.17 → 0.94，而該保護的案例完全沒動。criteria 的品質比門檻
的數字重要。

## 9. 兩個量過之後放心的地方

過濾過的上下文比原始上下文好，而且更便宜。把 25 則原始訊息整段丟進去，目標判
斷得到 0.25；先用一題把相關的挑出來再判，得到 0.59，同時 token 更少。這和
jaggedness #5 一致。

前提偵測器不會無中生有。擔心「問它有沒有前提，它就會編一個出來」。三個負面案例
（其中兩個是刻意設計的誘餌）量到 0.03–0.04。它沒有編。

## 11. 沒量到的

**召回率。** 上面每一個數字都是精確率那一側的：給定一個案例，模型判得對不對。漏判
需要真實漏抓的案例，而所有測試案例都是合成的。報告上的誤判／屬實按鈕累積的也只是精
確率。

這不是還沒做完的工作項，是這套方法論目前看不到的東西，所以寫在這裡而不是寫在
TODO 裡。
