# MessageWatch 架構決策

本檔案記錄 MessageWatch 的架構設計決策與工程取捨。指令操作與安裝說明請參閱 [README](../README.zh-TW.md)。分類模型背後的實測數據與問題設計，請參閱 [Jev 導入紀錄](jev-integration.zh-TW.md)。

---

## 1. 它做什麼、刻意不做什麼

MessageWatch 負責監控已啟用頻道中的近期訊息，評估對話互動是否需要人類管理員介入，並將結構化報告發送至指定的管理頻道。

本 cog 絕不自主執行懲處或修改動作。程式不會自動刪除訊息、不會自動禁言成員，也不會自動發送警告通知。所有管理動作皆必須由人類管理員在報告按鈕上主動確認：

- **稽核標記（`ok`、`no`）**：記錄管理員的回饋計數，供精確率統計使用。點擊者僅需具備檢視管理頻道的權限。
- **狀態處置（`del`、`mute`、`role`）**：執行目標訊息刪除、成員暫時禁言，或賦予特定管理身分組。點擊按鈕的管理員本人，必須直接持有對應的 Discord 權限（`manage_messages`、`moderate_members` 或 `manage_roles`）。

此項邊界設計源於本專案對過往實作缺陷的修正。本儲存庫曾包含一個名為 `phishingchecker` 的舊 cog，其懲處邏輯表面上看似完整，實際上從未運作：其封鎖與踢出分支嘗試呼叫 Red 3.5 中已不存在的 `modlog.case_create`（該版本僅提供 `create_case`），且從未真正呼叫過 `ban()` 或 `kick()`。

自動處置系統一旦出錯，會以靜默處罰無辜成員的形式造成危害；通報型系統一旦出錯，其失敗形式是靜默漏報，而漏報是人類管理員能夠即時察覺並介入的。

## 2. 判斷的單位是視窗，不是訊息

敵意、人際衝突以及說教等互動問題，皆屬於多則訊息交換過程中產生的整體性質，單一訊息抽離脈絡後往往無法反映真實語境。因此 MessageWatch 以滾動視窗（預設 `window_size = 8`）作為推論單位，而非逐則判定。

- **滿額視窗滑動保留一半（`take = 8`，`stride = 4`）**：佇列累積達 8 則訊息時觸發推論，取走 8 則後於佇列保留 4 則。若不保留 50% 重疊，橫跨視窗邊界的連續對話將會被截斷而失去脈絡。
- **短視窗全數清空**：由閒置掃描觸發的短視窗會整段取走。因為後續已無新訊息可供銜接，保留一半只會導致下一次掃描反覆判定相同的對話尾端。
- **單則訊息不予判定**：觸發門檻最低為 `MIN_PARTIAL_WINDOW = 2` 則訊息。單則發言不構成對話互動。

## 3. 湊不滿視窗的頻道

若系統強制要求累積滿 8 則才執行判定，低流量頻道（例如樹洞頻道中，一位成員發文抒發後僅有兩則簡短回應）將永遠無法觸發推論。然而此類安靜頻道往往正是最需要監控的場所。

為處理低活動量對話，系統透過 `tasks.loop(seconds=60)`（`IDLE_SWEEP_SECONDS = 60`）每 60 秒執行一次閒置掃描。掃描器會檢查佇列是否至少包含 `MIN_PARTIAL_WINDOW`（2）則訊息，且最新一則訊息的停留時間是否已超過該伺服器設定的 `idle_seconds`（預設為 600 秒）。當兩項條件皆成立時，系統會以 `partial=True` 將佇列送出判定。

| 訊息佇列狀態 | 判定時機 |
|---|---|
| 累積達 8 則以上 | 立即執行推論 |
| 累積 2–7 則後陷入沉寂 | 當沉寂時間達 `idle_seconds`（10 分鐘）時，於下一次 60 秒掃描週期執行 |
| 僅有 1 則訊息 | 絕不單獨判定；等待後續訊息達到 `MIN_PARTIAL_WINDOW = 2` |

在 `_sweep` 掃描流程中，未達 `MIN_PARTIAL_WINDOW` 的佇列會直接以 `continue` 跳過，不會傳入 `flush()`。若讓不足額佇列進入 `flush()`，會被 `_take_window` 攔截並在閒置頻道每分鐘記錄一次 `no_api_key` 或 `no_report_channel` 診斷紀錄，對原本用以辨識真正故障的診斷面板造成雜訊干擾。

閒置掃描同時負責將記憶體中的 token 消耗統計寫入磁碟（`_flush_usage`），並更新監控儀表板（`_update_dashboards`）。將這些維護任務附帶於既有的 60 秒循環中，可免除額外的計時器開銷。

## 4. 幾乎所有設定皆逐頻道獨立

頻道啟用狀態、自訂規則、頻道用途說明、違規判定門檻（`rule_threshold`）、報告發送目標（`report_channel`）、按鈕配置清單（`actions`）以及處置身分組（`action_role`）皆為個別頻道獨立設定。

這種獨立性是由樹洞與告解頻道（`#樹洞`）的實際需求所決定的。該類頻道的管理規則通常明文禁止心靈雞湯、下指導棋、分享自身經驗（「這我也遇過」）、揣測動機以及替人圓場。在通用詐騙或敵意模型判定下，此類發言的分數皆接近 0.0。此外，此類違規的適當處置既非刪除訊息亦非禁言，而是加上能隱藏該頻道的隔離身分組。將這些特殊規則或處置按鈕配置於一般討論頻道將完全不合適。

門檻繼承採用 `channel_value or guild_value` 邏輯。頻道設定中儲存的 `0.0` 代表繼承伺服器全域設定，而非將門檻設為零。

## 5. 揭露契約與版本

`messagewatch.py` 程式碼中的 `DISCLOSURE_VERSION` 目前為 4。若伺服器管理員所同意的揭露版本與此常數不符，本 cog 會暫停該伺服器的所有對外推論傳輸，直到管理員使用 `[p]watch disclosure I_ACCEPT` 重新確認為止。各版本是累加的：第 1 版是訊息文字的基礎傳輸，第 2 版加入頻道規則與用途說明，第 3 版加入互動處置按鈕與其 modlog 紀錄，第 4 版加入影像判讀。因此所有已接受第 3 版的伺服器都會停擺，直到有人接受第 4 版為止。

每當離開 Discord 的資料範圍變更時，契約版本隨之推進：
1. 第 1 版：核心訊息文字與頻道名稱。
2. 第 2 版：頻道自訂規則與管理員撰寫的用途說明。
3. 第 3 版：互動處置按鈕、權限檢查與管理日誌紀錄。

當版本遞增後，所有伺服器將暫停對外發送。為避免無聲停擺，`[p]watch show` 會在面板首個欄位明確指出當前狀態為揭露版本過期而暫停。

資料揭露宣告文字同時同步於四處：`messagewatch.py` 的 `DISCLOSURE_TEXT`、`info.json` 的 `end_user_data_statement`、[README](../README.zh-TW.md)，以及通報報告 embed 頁尾。單元測試 `test_messagewatch.py` 會比對 `DEFAULT_CHANNEL` 的欄位集合與宣告詞彙對照表，若新增儲存欄位而未於揭露文字中說明，測試將無法通過。

## 6. 並行控制：單一鎖從頭鎖到尾

頻道評估常式 `flush()` 在其整段執行期間（包含外部網路請求與報告送出）全程持有 `self._locks[channel.id]`。

在早期原型中，鎖僅在自佇列取出視窗時持有。這導致在取出訊息至發出報告之間存在並行空窗。若管理員在該空窗期執行 `[p]watch disable` 停用頻道，已被取出的訊息仍會被傳送至外部 API 並發出報告。

將鎖的範疇擴展至包覆整個方法體，消除了這項競爭條件。推論期間該頻道的訊息接收僅短暫暫停，新收到的訊息會在釋鎖後排入 `self._pending[channel.id]`。此外，`flush()` 在發送前會在鎖內重新確認 `watched_channels` 狀態。因為 `[p]watch disable` 亦需取得同一個鎖，它無法與那次重讀交錯：在重讀之前被停用的頻道不會送出任何東西。但它取消不了已經在途中的請求——`flush` 連同 provider 呼叫一起持鎖，所以停用指令會等那次呼叫結束，該次產生的報告仍會送出。

## 7. 外部模型輸出視為不可信

所有來自外部供應商的推論回應，皆透過防護常式進行驗證與範圍限縮：`_bounded_probability`、`_bounded_score`、`_bounded_index` 與 `_bounded_token_count`。

這些轉換防護是為了解決開發過程中實際遭遇的 4 種資料解析崩潰：

- `float(10**400)`：`json.loads` 解析過大整數後，轉浮點數時拋出 `OverflowError`。
- `int("²")`：`"²".isdigit()` 判定為 `True`，但在 `int("²")` 轉型時拋出 `ValueError`。
- 過度深層的巢狀 JSON：導致 `json.loads` 拋出 `RecursionError`。
- `int(float("inf"))`：`json.loads` 將字串 `Infinity` 轉為浮點無窮大，轉整數時拋出 `OverflowError`。

數值範圍檢查一律採用封閉區間比對：`if not low <= parsed <= high`，絕不寫成 `if parsed < low or parsed > high`。後者在遇到 `NaN` 時兩個比對皆會回傳 `False`，導致非法數值通過過濾，使後續的 `probability < threshold` 判斷全面失效。

## 8. 處置權限完全留在人類管理員手上

通報報告上的互動按鈕採用 persistent view 實作。每顆按鈕將操作環境編碼於結構化 `custom_id` 中：

```text
mw:<action>:<kind>:<channel>:<message>:<author>
```

以三個 20 位數的 snowflake 與最長的動作名稱（`role`）實測，長度為 72 個字元，低於 `CUSTOM_ID_LIMIT = 100`，`build_custom_id` 在建構時就斷言這件事。在真的跑過建構函式之前曾有兩個較小的數字流通──本文件早期草稿寫 69、原始碼註解寫 71──兩者都是讀程式碼推出來的，不是量出來的。雖然 `discord.py` 在用戶端未驗證 100 字元上限，Discord API 端會嚴格阻擋。按鈕處理常式在啟動時於 `cog_load` 透過 `bot.add_view` 重新註冊，使機器人重新啟動後，舊報告上的按鈕仍可持續運作。

`ACTIONS` 對照表定義了各動作對應的 Discord 必要權限：

| 動作識別碼 | 按鈕標籤 | 按鈕樣式 | 必要 Discord 權限 |
|---|---|---|---|
| `ok` | 屬實 | `secondary` | 無（僅記錄稽核計數） |
| `no` | 誤判 | `secondary` | 無（僅記錄稽核計數） |
| `del` | 刪除訊息 | `danger` | `manage_messages` |
| `mute` | 禁言作者 | `danger` | `moderate_members` |
| `role` | 加上身分組 | `danger` | `manage_roles` |

按鈕 callback 會直接檢查觸發者的 `guild_permissions`，確認該成員確實持有對應的伺服器管理權限，而非僅以能否檢視管理頻道作判定。實際處置紀錄會寫入 Red 的 `modlog`，並署名執行該動作的管理員。

## 9. 儲存與未儲存的資料範疇

### 儲存項目
- 伺服器全域設定與通報報告頻道 ID。
- 明確啟用的頻道 ID 集合。
- 頻道專屬規則、用途說明、報告路由目標、按鈕配置清單與處置身分組 ID。
- 各項分類門檻（`scam_threshold`、`hostile_threshold`、`heat_threshold`、`rule_threshold`、`rule_confidence`）。
- 管理員標記累計計數（依類別分類的 `ok` 與 `no` 總數）。

### 排除儲存項目
- 原始訊息文字內容。
- 外部模型推論原始回應。
- 單次判斷的中間運算結果。

管理員標記機制能讓系統隨運作累積精確率數據。然而，**召回率目前仍無法量測**。計算偽陰性（漏判）需要得知未被通報的違規發言，而報告按鈕無法觸及未通報的事件。現行門檻數值皆來自合成測試案例的量測校準，而非生產環境召回率。

## 10. 影像輔助管線設計（image aux）

Jev 模型僅處理文字資料。由於 Discord 上的詐騙發言常以純截圖形式呈現，MessageWatch 設計了一套輔助的多模態影像處理管線，其契約明確限定為逐字字元轉錄。

該模型僅執行逐字 OCR 轉錄，不進行開放式畫面描述。開放式描述屬於未校準的生成文字，管理員難以對照原圖檢核；逐字轉錄則可直接顯示於通報報告上供人類核對。轉錄所得文字會接回現有的詐騙判定題目，因此圖片文字會依序發送至視覺模型端點與 TypeSafe，揭露文字中已明確聲明此傳輸路徑。

運作規格：
- 圖片送出前等比例降採樣至長邊上限 1536 px 並重新編碼，去除包含 GPS 在內的 EXIF 詮釋資料。
- 每個視窗上限 4 張圖片，單張圖片大小限制 8 MB 且解析度上限 4000 萬像素。
- 依附件 ID 快取於記憶體中，上限 256 筆。因快取不含使用者識別資訊，於 `cog_unload` 與 GDPR 資料刪除請求時一律清空全數快取。
- **未配置預設視覺模型**。各多模態模型對中日韓截圖的文字辨識準確率尚未取得實測基準，在管理者手動設定前此管線保持停用。

視覺端點與模型名稱儲存於全域設定中，僅限 bot owner 透過 `[p]watch vision` 設定。由於視覺 API 消耗全域憑證，限制僅 owner 可修改能防止個別伺服器管理員將金鑰或圖片資料導向非授權伺服器。`api_base` 必須使用 `https://` 協定。

## 11. 成本可見性

資源消耗量（包含 input tokens 與累計判定視窗數）暫存於記憶體中，每 60 秒隨閒置掃描寫入磁碟，並在 `cog_unload` 時再次保存。非預期重啟最多僅損失最後 60 秒的統計尾數。管理員可透過 `[p]watch dashboard` 在指定頻道釘選即時更新的監控面板。

## 12. 尚未解決的架構限制

- **召回率仍未量測**：系統透過標記按鈕追蹤精確率，但無法量化線上環境的漏判率。
- **缺乏視覺模型基準量測**：不同多模態模型在中日韓截圖上的轉錄準確度尚未建立量測數據。
- **卸載時無法取消派發任務**：已進入 `discord.py` 派發佇列的 `flush()` 任務無法在 `cog_unload` 時強制中止，卸載後可能仍會發送最後一份在途報告。
